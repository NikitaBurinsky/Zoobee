# ADR-0001: Documentation System For MVP + Growth Foundation

- Status: `accepted`
- Date: `2026-04-21`
- Deciders: `Project Owner`, `Codex`
- Technical Story: `DOC-001..DOC-037`

## Context

Проект эволюционирует из solo-разработки в командную работу людей и AI-агентов.
Документация была фрагментированной и частично устаревшей (локальные docs, legacy entrypoints, неявные решения).
Нужен единый, трассируемый и практически применимый контур docs для MVP с фундаментом роста.

## Decision

1. Ввести централизованный docs hub в `/docs` как source of truth.
2. Фиксировать не только целевую картину, но и фактические долги/риски.
3. Ввести status taxonomy систем: `Active/Legacy/Stale/Experimental/Planned`.
4. Использовать classic ADR как обязательный механизм значимых решений.
5. Ввести обязательный docs-impact gate в PR процессе.
6. Зафиксировать ambiguity protocol: `block-and-ask`.
7. Для MVP принять временную политику локализации: без приоритета полноты локалей.

## Consequences

### Плюсы

- Быстрый онбординг новых людей и AI-агентов.
- Прозрачная трассируемость решений и долгов.
- Снижение риска «устного» знания и рассинхронизации.

### Минусы

- Дополнительная дисциплина при каждом архитектурном изменении.
- Накладные расходы на поддержание backlog/ADR в актуальном состоянии.

### Риски/компромиссы

- Пока high-risk технические долги открыты, документация не заменяет stabilization work.
- Временная локализационная политика может ухудшать UX до отдельного i18n этапа.

## Alternatives Considered

1. Оставить docs распределенными по модулям без центра.
2. Документировать только «целевую» архитектуру без фиксации долгов.
3. Не вводить ADR и решать архитектуру через комментарии в PR.

Все альтернативы отклонены как недостаточные для масштабирования команды.
